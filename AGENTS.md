# AGENTS

This repo follows the shared engineering standards vendored at [`standards/`](standards/)
(a git submodule). **Read [`standards/AGENTS.md`](standards/AGENTS.md) first** — it is the
entrypoint and indexes every rule.

- **Archetype:** cli-tool — see `standards/docs/archetypes/cli-tool.md`.
- **Identifier:** `dev.thmsn.linear-cli`
- Treat the standards as binding defaults. Repo-specific overrides (if any) are noted
  below; everything else defers to `standards/`.

## Repo-specific overrides

Intentional deviations, with reasons. Everything not listed here defers to `standards/`.

**This is a TypeScript/npm CLI, not a Rust one.** The `cli-tool` archetype is the right
category — a standalone binary distributed to machines — but its concrete requirements assume
Cargo. It follows the *shape* of the standards rather than the Rust mechanics:

| Standard | Status here |
|---|---|
| [Rust conventions](standards/docs/rust-conventions.md) | **N/A.** TypeScript, bundled with esbuild to a single CJS file. `tsc --noEmit` with `strict` is the lint gate. |
| [`lib*` ecosystem](standards/docs/lib-ecosystem.md) | **N/A.** No `libconfig`, `liberror`, `libsignal` or `libbuildinfo` — those are Rust crates. |
| [Configuration](standards/docs/configuration.md) | Follows the *precedence* rule (env over file) without `libconfig`: `LINEAR_API_KEY` overrides `~/.config/linear-cli/config.json`. |
| [Error handling](standards/docs/error-handling.md) | No `thiserror` trinity. Errors map to a stable `{"error","code"}` JSON envelope on stderr with exit 1 — see the error-code table in the README. |
| [Identifiers](standards/docs/identifiers.md) | `dev.thmsn.linear-cli` is recorded here but not surfaced at runtime; there is no `libproduct` for Node. Deferred, as in `igrip`. |
| [CI/CD](standards/docs/ci-cd.md) | **Compliant on naming and the gate.** `ci.yml` on `push: main` + `pull_request` with `concurrency` cancel; delivery is `cli.release.yml` per the `<component>.<action>.yml` rule. Runs on GitHub-hosted runners rather than self-hosted — see the release note below. |
| [Versioning](standards/docs/versioning.md) | **Compliant.** `MAJOR.MINOR.<commit count>` derived by `scripts/version.sh` and injected at build time; `package.json` holds a static `0.0.1` placeholder. |
| [Workflow](standards/docs/workflow.md) | **Compliant.** Commits go straight to `main`. |
| [Testing](standards/docs/testing.md) | **Compliant in spirit.** 102 tests over the JSON output contract, error mapping, pagination and arg parsing — the surfaces the archetype names. No coverage gate is wired up. |

### Open gaps

Real deviations rather than N/A, listed so they are not mistaken for done:

- **Released to GitHub Releases, not the registry.**
  [registry-publishing.md](standards/docs/registry-publishing.md) is the defining standard for
  this archetype: publish to `apps.dev.thmsn.dev` as `kind = cli` with an install manifest,
  built per-target on self-hosted runners. `cli.release.yml` instead publishes a single
  `linear.js` to GitHub Releases from a GitHub-hosted runner.

  The reason is that the registry's machinery buys nothing here. The artifact is one
  platform-independent JS file — no per-target matrix, no signing or notarization — so there is
  no multi-artifact selection for an install manifest to do. Deliberate; revisit if this ever
  ships a native binary.

  Local development still uses `npm install -g .`, which symlinks the global bin into the
  working tree, so a build in a clone is immediately live.
- **No shell completions.** The archetype expects them shipped or generated by a subcommand.
  Commander can generate them, but nothing is wired up.
